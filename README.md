# Calendar

REST-сервис на Spring Boot, который строит григорианский календарь на
заданный год и определяет день недели по произвольной дате.

## Ответ на исходный теоретический вопрос

Раскладка календаря на год зависит только от двух параметров: дня недели
1 января (7 вариантов) и високосности года (2 варианта). **7 × 2 = 14**
уникальных календарей существует независимо от конкретного года — эта
идея прямо отражена в архитектуре: `CalendarStorage` не пересчитывает
календарь заново на каждый запрос, а хранит и переиспользует одну запись
на каждую из 14 возможных комбинаций (см. "Как это работает" ниже).

## Архитектура

```
com.ilyanin.calendar
├── CalendarApplication.java          — точка входа Spring Boot
├── api/controller
│   └── CalendarController.java        — REST-эндпоинты
├── exception
│   ├── GlobalExceptionHandler.java    — единообразные JSON-ответы об ошибках
│   ├── UnsupportedYearException.java
│   ├── UnsupportedExportFormatException.java
│   └── CalendarExportException.java
├── model                              — доменные модели (record'ы, без логики персистентности)
│   ├── Calendar.java / Month.java / Day.java
│   ├── MonthName.java / WeekDay.java
│   └── CalendarKey.java               — ключ одного из 14 уникальных календарей
├── service                            — бизнес-логика и точки расширения
│   ├── CalendarSystem.java            — абстракция календарной системы (григорианская/юлианская/...)
│   ├── GregorianCalendarSystem.java   — единственная реализация сейчас
│   ├── CalendarFactory.java           — строит Calendar по ключу, резолвит ключ по году
│   ├── CalendarStorage.java           — абстракция хранилища 14 календарей
│   ├── CalendarService.java           — фасад: получить календарь, получить день недели
│   ├── CalendarExporter.java          — абстракция формата ответа (JSON/XML/XLSX/...)
│   ├── JsonCalendarExporter.java      — единственная реализация сейчас
│   └── CalendarExporterResolver.java  — выбор нужного CalendarExporter по формату
└── persistence
    ├── CalendarEntity.java / MonthEntity.java / DayEntity.java  — JPA-сущности
    ├── CalendarEntityMapper.java      — преобразование Entity ↔ доменная модель
    ├── CalendarRepository.java        — Spring Data репозиторий (JOIN FETCH)
    └── JpaCalendarStorage.java        — реализация CalendarStorage поверх JPA/H2
```

### Почему так разделено

Каждый интерфейс в `service/` — самостоятельная ось расширения, не
связанная с остальными:

| Абстракция        | Отвечает за                          | Точка расширения                          |
|--------------------|----------------------------------------|--------------------------------------------|
| `CalendarSystem`    | Правило високосности и день недели      | Юлианский календарь и другие системы        |
| `CalendarStorage`   | Где хранятся 14 календарей              | Любая другая БД или in-memory-реализация    |
| `CalendarExporter`  | В каком формате отдать календарь        | XML, XLSX и другие форматы                  |

Контроллер и сервис работают только через эти интерфейсы. Чтобы добавить
новый формат экспорта, достаточно одного нового класса
`implements CalendarExporter`, помеченного `@Component`, — он
автоматически появится в `List<CalendarExporter>`, который использует
`CalendarExporterResolver`; ни контроллер, ни существующие экспортёры не
меняются.

С `CalendarSystem` есть нюанс: сейчас Spring внедряет единственный бин
напрямую, без механизма выбора между несколькими реализациями (в отличие
от экспортёров, где такой механизм уже есть). Технически интерфейс уже
Strategy и новую реализацию (например, юлианский календарь) добавить
легко, но чтобы иметь возможность выбирать между несколькими системами
**за один вызов**, потребуется добавить резолвер по аналогии с
`CalendarExporterResolver` — сейчас это не сделано, так как реализация
всего одна.

### Домен vs persistence

`CalendarEntity`/`MonthEntity`/`DayEntity` — это JPA-сущности, полностью
отделённые от доменных `Calendar`/`Month`/`Day`. Единственное место,
которое знает про обе стороны, — `CalendarEntityMapper`. Остальной код
(сервисы, контроллер) не видит JPA-аннотаций вообще.

## Как это работает

1. Клиент запрашивает `GET /api/calendars/{year}`.
2. `CalendarSystem` определяет день недели 1 января этого года и
   високосность — вместе они образуют `CalendarKey`, один из 14
   возможных.
3. `CalendarService` ищет календарь с этим ключом в `CalendarStorage`
   (таблица `CALENDARS` в БД).
   - Если найден — возвращается сохранённая запись, ничего не
     пересчитывается.
   - Если нет — `CalendarFactory` строит календарь (12 месяцев, дни
     через `WeekDay.next()` по кругу от 1 января) и сохраняет его
     каскадно (1 запись в `CALENDARS` → 12 в `MONTHS` → 365/366 в
     `DAYS`) для всех последующих запросов с тем же ключом.
4. `CalendarExporterResolver` находит `CalendarExporter`, поддерживающий
   запрошенный `format` (сейчас только `json`), и сериализует ответ.

Год вне диапазона, поддерживаемого григорианской системой (`< 1600`),
отклоняется `UnsupportedYearException` ещё до обращения к хранилищу —
запись в БД в этом случае не создаётся.

`java.time.LocalDate` используется как проленптический григорианский
календарь (ISO-8601): в нём есть год `0`, которого нет в исторической
BCE/CE-хронологии, и все правила високосности применяются "назад"
математически, а не исторически. Ограничение `>= 1600` частично снимает
эту неоднозначность, но само по себе не делает вычисления историческими
для более ранних периодов, чем реально существовал григорианский
календарь.

## Известные особенности (осознанные, не баги)

- Если в одном запросе год валиден, но запрошенный формат экспорта не
  поддерживается, `CalendarService` успевает построить и сохранить
  календарь в БД до того, как `CalendarExporterResolver` бросит
  `UnsupportedExportFormatException`. Это признано безопасным: множество
  всех возможных календарей конечно (14) и полностью детерминировано —
  лишняя запись не может испортить данные, только предвычислить то, что
  и так рано или поздно будет запрошено с корректным форматом.

## API

### `GET /api/calendars/{year}?format=json`

Возвращает календарь на указанный год.

```bash
curl "http://localhost:8080/api/calendars/2026?format=json"
```

### `GET /api/weekday?date=2000-01-01`

Возвращает день недели для даты (формат ISO-8601, `YYYY-MM-DD`).

```bash
curl "http://localhost:8080/api/weekday?date=2000-01-01"
```

Оба эндпоинта возвращают `400` с единообразным JSON-телом
(`GlobalExceptionHandler`) при некорректном годе, дате или формате.

## Запуск

### Через Maven

```bash
./mvnw spring-boot:run
```

### Тесты

```bash
./mvnw test
```

Юнит-тесты покрывают `GregorianCalendarSystem`, `CalendarFactory`,
`CalendarService` (вся оркестрация — с моками зависимостей),
`CalendarExporterResolver`, `JsonCalendarExporter` и
`CalendarEntityMapper`.

### Через Docker

```bash
docker compose up --build
```

Поднимает сервис на `http://localhost:8080`. `--build` пересобирает
образ — необходимо после любого изменения в `src/` или `pom.xml`, так
как компиляция происходит внутри Docker-образа на этапе `docker build`,
а не при каждом запуске контейнера.

### H2-консоль

Доступна на `http://localhost:8080/h2-console` (JDBC URL:
`jdbc:h2:mem:calendar`, user: `sa`, без пароля).

`spring.h2.console.settings.web-allow-others: true` в
`application.yml` — осознанно снятая защита H2 от "удалённых"
подключений, необходимая при обращении к консоли через проброшенный
Docker-порт. Приемлемо для локальной разработки, но не должно
попадать в конфигурацию для реального внешнего окружения.
